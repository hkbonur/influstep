# Influstep: plan

Written 2026-10-09. The goal: Formstep gets attention and users through AI personas the operator owns, instead of ads or paid influencers. Later, the same software as a product for other companies.

## How a persona works

A persona is a profile (name, handle, voice, niche, tone, platforms, content pillars, sponsor dial). Five agent roles do its work, each as jobs the operator can see:

| Role       | Runs on          | What it does                                                                                                                                                  |
| ---------- | ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| researcher | backend (hourly) | Polls Hacker News, Reddit, Google Trends, YouTube search, and the persona's own comments. Stores signals with topics and a score.                             |
| writer     | backend          | Plans the week (which concept on which day, which experiment variant, sponsored or not), writes the script from a signal or a pillar and the open directives. |
| producer   | runner           | Records screen shots with Playwright recipes in the operator's signed-in browser, generates the voice, renders 16:9 and 9:16 with captions.                   |
| publisher  | runner + backend | Uploads at the scheduled time with the tracked link and the AI-disclosure label, then reads comments back as signals.                                         |
| analyst    | backend (daily)  | Snapshots platform metrics, clicks, and PostHog conversions; decides experiments; writes the report.                                                          |

An episode moves through: idea → scripted → (waiting on you) → recording → rendered → scheduled → published → measured, or failed / killed. Scripts wait for the operator's approval unless the persona auto-approves.

When an agent cannot continue (n8n not signed in, YouTube permission missing), it creates a checklist item that names the episode it unblocks. Items with a runner action ("Open the runner's browser to sign in") carry a button.

## What is built (v0.1, local, mock providers)

- `packages/shared`: episode status machine, job kinds, provider contracts, UTM and slug helpers, experiment statistics.
- `packages/convex`: schema; core rules (pipeline transitions, weekly planner, experiment decision, attribution); operator API; agent actions; job dispatch with a runner HTTP route; crons; providers (mock + real where no key is needed); seed.
- `apps/studio`: Calendar (home), Personas (chat with directives, script editor with approval, checklist, settings), Experiments, Signals, Checklist, Reports (funnel + trend per persona), Providers; Worker with `/go/:slug` and `/p/:handle`.
- `apps/runner`: polls jobs; mock producer renders a placeholder video with ffmpeg; real producer records with Playwright `recordVideo`; uploads to Convex storage; heartbeats.
- Tests: pipeline, planner, experiment statistics, attribution, worker routes.

## v0.2: autonomy and value

Written 2026-10-10 after the operator's second brief. The product in one sentence: highly customizable personas, each with shared agents it directs, that evolve on their own data into creators who bring Formstep paying customers. The question every screen must answer: did a video move Formstep? Built in this order, each slice shipped on its own. Slices 3, 4, 5 and 11 were added on 2026-10-13, when the operator asked for X, for taking over an existing X account, and for every persona in the sidebar; slice 15 was added the same day, when the operator asked how the personas would make images and video.

1. **Value per episode.** Conversions cover the whole Formstep journey: demo started, signup, trial started, paid. Each one records whether it came through a tracked link (UTM) or a discount code. Codes are the operator's: created in Polar by hand and handed to a persona in chat ("use code ADA20 for the next video") or in its settings; a persona never mints one. Influstep puts the code in descriptions and counts its redemptions. The workspace holds a value per paid conversion, so the report can estimate what a persona and an episode earned. Every publication's description carries the Formstep line, the code when there is one, the tracked link and the AI disclosure, whatever the sponsor segment says about the video itself.
2. **Platform specialists.** A persona publishes only where it is set to publish. The roster can hold a TikTok-only persona, a YouTube specialist, and one that posts everywhere, and nothing is ever queued for a platform a persona does not have. Each persona carries a format per platform it uses: target length (a 30-second TikTok, an eight-minute YouTube tutorial), aspect, delivery (talking head, screen recording with a corner avatar, screen only), and a hook convention. Onboarding starts from per-platform defaults the operator edits (TikTok: 20 to 45 seconds, vertical, hook in the first two seconds; YouTube: 3 to 10 minutes, wide, a screen tutorial with chapters; Instagram: 30 to 60 seconds, vertical). An episode is one script for the platforms it goes to (all of the persona's by default, narrowed per episode): its length is the shortest target among them, its delivery the one of the longest-form platform, and that format is stored on the episode when it is scripted so a later settings change does not alter a written script. Delivery decides the shots: a talking-head persona never records a screen and never waits on a sign-in. Every agent reads the format: the writer writes to the length and the delivery, the producer records only the cuts that persona's platforms need, publish-time defaults and experiments are per platform, and the report compares a persona against its own platforms, so a YouTube specialist is judged on watch time and tutorials and a TikTok specialist on hooks and shares, not on the same bar.
3. **Personas in the sidebar.** Every persona is a row in the left sidebar with its own avatar, the way an assistant app lists its bots, so the persona the operator talks to is one click from anywhere. The avatar is Formstep's AI mascot in the persona's own color, chosen from eight identity colors when the persona is created. A row shows at most one mark: how many things wait on the operator for that persona, or a red dot for a failed episode. Avatars in the sidebar and in lists are still pictures; the mascot shows its three thinking dots while one of the persona's agents works, and only the persona's own page shows it alive (looking around, blinking), so nothing moves while the operator reads a report.
4. **X, where a persona also writes.** X joins the platforms. A persona set to X publishes its videos there and, unlike on the video platforms, also posts without a video: a text post, an image post (a title card or an asset from the library, made by the producer the way a render is), or a thread. An episode therefore has a kind, video or post; a text post skips recording, an image post records only its image, and posts share the calendar, the chat, approval, the report and the experiments with video episodes, so the planner, the writer and the analyst treat a post as one more format. The X format adds a cadence (posts per day, the mix of kinds) next to the length and delivery every format has. Every X account Influstep runs carries X's label for automated accounts, the same posture as the AI disclosure on videos. Nothing is appended on X: a post is only what the persona wrote, with no sponsor line, tracked link or code, and a video's X text is its title, so X traffic reaches Formstep through the bio link and the persona's own words. Real adapter: the X API v2 (post, media upload, post metrics); the mock publisher returns fake post ids until the keys exist. Limits and prices of the X API tiers are checked when the keys are set up, not assumed here.
5. **Take over an X account.** An X persona can take over an account that already exists and keep sounding like it. The operator connects the account and brings its history: the X data archive (`tweets.js` from "Download your data"), posts pasted by hand, or the timeline through the X API once keys exist (the mock serves plausible history from the persona's niche until then). The analyst reads that history and writes the persona's voice: the language it posts in, how long its posts run, its tone and recurring moves, how it uses line breaks, lists, emoji and hashtags, and a handful of its own posts as examples. The operator edits the voice in place, and every X post is written in that language and that style, with the example posts in front of the writer. Posts vary on purpose: each one has an intent (ask a question, inform, share something found, teach a how-to) and a length (a one-liner, a full post, a thread), and the planner mixes both across the week from the voice's own length mix, so the feed reads like a person and not a schedule. Topics are anything in the niche, from the pillars and the day's signals, not only the sponsor; the sponsor dial still decides how often Formstep comes up, and when it does it is in the persona's own words. The imported posts with the most engagement are the first evidence of what works for this account; intent and length join the experiment dimensions.
6. **Preview before publish.** A rendered episode waits as a publish package (video per aspect, per-platform title and description, time) until the operator approves it, unless the persona is set to publish on its own. The text the operator edits is the persona's own title and description; the footer (the Formstep line, the code, the tracked link, the disclosure) is composed at dispatch, so an edit is never overwritten and a code change reaches every package that is not live yet, drafts included. Operator edits to the script must reach the beats the voice track is built from (today updateScript patches hook and script but not shotPlan, so the recording speaks the writer's text); the editor edits the beats, and the script view is derived.
7. **Chat that changes the plan.** "Replace Tuesday's n8n episode with one about Make", "move Friday to Saturday", "drop the webhook one": the persona interprets, applies, and says what it did. Agent tasks from the same chat: a research brief, a comment digest, an analytics summary, each run by the role that owns it and posted back as a message. Agents are workers of the workspace, not of one persona: one researcher, writer, producer, publisher, analyst serve every persona, each with a queue the operator can see on an Agents page (what each worker is doing now, for whom, what it did last), and a persona tasks a worker the way a creator would brief an assistant.
8. **Strategy review.** The analyst reviews each persona weekly: pillar weights, publish hour per platform, and which experiment to run next. Every change has a reason and evidence and shows up in the persona's journal; the planner follows the current strategy. The persona picks its own experiments from a catalog of strategies (hook style, concept, sponsor placement, publish time, description format, episode length, call to action), preferring the dimension it knows least about, the metric closest to the goal (paid over signups over clicks over views), and never more than one running experiment per persona. When an experiment decides, the winner becomes the persona's default for that dimension (the hook style it opens with, the hour it posts at, the description format), the decision is written to memory as a learning with the experiment as evidence, and the writer reads that learning before the next script. A winner that later data contradicts is re-tested, not trusted forever.
9. **Fresh research, like a real creator.** A persona works the way a working creator does: before it decides what to record it goes online. Search suggestions join the signal sources, so episodes answer what people type. Every signal carries a freshness score that decays by the day, and the researcher runs a morning sweep per persona that writes a short daily brief to memory (what moved in the last 24 hours across forums, search, trends, and the persona's own comments) and expires it the next day. Scripts are written just in time, the day before the publish slot, not when the week is planned, and the writer asks the researcher for a last check ("is this still what people ask?") before it writes; a concept that went cold is swapped for the day's strongest signal and the journal says so. Problems the persona meets itself (a tool that broke in a recording, a question repeated under its videos) become a problem log in memory, and a logged problem is a concept candidate with a high score. Experiment kinds for publish time and description format (code versus link) ship in the same slice.
10. **Memory and assets.** Each persona keeps a memory: short entries the persona and its agents write and read, each with a kind (learning, fact, rule, goal note), the evidence it rests on (episode, experiment, signal, or the operator's message), a confidence, and a status (active, superseded). The writer reads active entries with the bible and the directives before every script; the strategy review reads them before it changes anything and writes a new learning for every change it makes; the chat can store one ("remember that viewers hate the word 'guys'"). Entries that later data contradicts are superseded, never deleted, so the persona can show why it believes something. The workspace holds the one goal every persona optimizes for, paying Formstep customers, and each strategy review records where the persona stands against it (value this window, trend, what it will try next). Each persona also has an asset library in Convex storage: images, clips, audio, documents, uploaded by the operator or saved by the producer (renders, voice tracks, title cards), each with tags and a note; the writer can ask for an asset in a shot ("show the pricing screenshot") and the producer places it.
11. **Engagement on X.** An X persona also grows by answering other people. A listener (the researcher's X sweep) finds posts in the persona's pillars worth answering: recent, from accounts with reach, not yet answered by the persona, and never about the sponsor unless the operator asked. The writer drafts the reply inside the bible, the directives and the persona's memory, and it goes out within a daily reply budget. X's automation rules decide who presses the button: a reply to someone who engaged with the persona first (a reply under its post, a mention) can go out on its own, while a reply to a stranger's post found by the listener is a draft until the operator posts it, one click per reply, never in a batch and never automatically, because X forbids automated replies chosen by keyword search. Influstep never likes, reposts or follows on its own. The operator can set rules in chat ("never reply to politics", "only reply to people building agents"). Every reply is an engagement row: the post it answered and its author, the reply, when it went out, and what it brought back (likes, replies, profile visits, follows), pulled by the analyst. The report shows engagement as its own block (replies sent, follows per reply, the replies that brought followers), the strategy review treats reply style, reply targets and post kind as experiment dimensions, and what works becomes a learning in memory, so an X persona grows its account on its own data. Listening needs X API search access; the mock listener serves plausible posts from the persona's topics until it exists.
12. **Analytics, top down.** Reports open on the workspace: one funnel for every persona together (views, follows, clicks, demos, signups, trials, paid, value) for the window, an engagement line (likes, comments, watch rate, follows per view), and a persona table with the same columns so the operator sees in one glance who brings paying customers and who only brings views. One click drills into a persona (the existing report), one more into an episode (the value block). Every number keeps its provenance: platform counts, exact clicks and redemptions, attributed PostHog conversions. Three "what works" lists computed from measured episodes across personas: by pillar, by hook style, by sponsor segment, each ranked by value then clicks per view, so the operator and the strategy review read the same facts. Bio-link clicks are persona-level today, so TikTok and Instagram rows show zero clicks outside the seed; give each platform its own bio slug (/p/<handle>?via=<platform>) so the By platform table can carry them.
13. **Onboarding.** A first-run flow that builds the roster instead of a blank form: how many personas, then one step per persona. Each step asks for the niche and the audience, proposes a name, handle, tone, pillars and a bible the operator edits in place, and asks for the look: a style (cartoon presenter, photoreal presenter, or screen-only with a voice, Loom-style with a small corner avatar), reference images or a short reference video uploaded to the asset library, and a voice (an ElevenLabs voice id, or a description the voice provider turns into one). The look becomes the persona's appearance profile; the avatar provider reads it for every take (mock renders a title card in the chosen style until a provider key exists). The flow ends with the platforms and the format for each one, the sponsor dial and the posting hours, then plans the first week. The same flow adds one more persona later.
14. **Home dashboard.** The calendar stays the plan for the week; above it a short overview answers the operator's three questions in one glance: what waits on me (checklist and approvals), what the personas changed on their own this week (journal), and what it earned (value per persona for the window, with the attribution caveat). One screen, no widget grid.
15. **Generated media.** The producer can make the pictures a beat needs, not only find them in the asset library. A media provider joins the providers, with a mock and a real adapter like the others: an image model for stills (OpenAI's image API, gpt-image-1 to start) and a video model for short clips (Seedance). The writer can ask for a generated image or clip in a beat with a prompt where it would otherwise name an asset ("a run history where every execution fails in red"), inside the bible, the rules and the persona's look, and never in the sponsor demo beat, where Formstep's real screen shows. Before recording, a backend job generates it (a video model is polled until the clip is done) and saves it to the asset library as the producer's, tagged generated, with the prompt and the model in its note, so it is reused, edited and deleted like any asset, and the beat shows it as an asset shot. The operator can also generate an asset from a prompt on the Assets page, and generate one again when it misses. Nothing generated pretends to be real: a prompt for a real person, a brand other than Formstep, or a real product's screen is refused, since a screen made up by a model would mislead a viewer about how the tool works; a tool's real screen is recorded. Generation has a daily budget per persona (images and seconds of video), shown with the provider on the Providers page, and a job that would pass it fails with the budget in its error. Generated media goes out under the same AI labels as everything else. The mock provider draws a placeholder (the prompt on a card in the persona's color; a still held for a clip), so the whole path runs without keys; in real mode a missing key is an error, never a fallback to mock (ADR 0002). Which models, their limits and their prices are checked when the keys are set up, not assumed here.
16. **Polish.** An impeccable pass (critique, then polish) over every screen against DESIGN.md, then the cleanup skill over the changed files. Smoke test in Chrome at desktop and phone width.
17. **Avatars from a portrait.** Added 2026-10-16 when the operator chose an avatar provider. A persona with a presenter has a portrait, the first image of its look: uploaded, or drawn by the media provider (gpt-image-1, square) from the operator's description of the presenter, at onboarding or on the Assets page, in the look's face. HeyGen Avatar IV animates that portrait to the persona's own ElevenLabs track, so a persona keeps one face and one voice; OpenAI cannot animate it (its Sora video API closed on 2026-09-24). Each presenter beat is one square take of its stretch of the track, fitted to every cut, so a video with two cuts pays once. Loom-style is a look of its own: the screen the whole video with the presenter in a round bubble in the bottom-left corner, cut from one take over the whole track, which also serves its full-frame presenter beats; its face is cartoon or realistic, the operator's pick. In mock mode a take is a card with the portrait and a Loom bubble is the portrait held as a still; in real mode a video with a presenter and no portrait fails saying what to do.

### Autonomy loop

What runs on its own, per unpaused persona:

| When             | Job                   | Role       | Writes                                         |
| ---------------- | --------------------- | ---------- | ---------------------------------------------- |
| hourly           | poll_signals          | researcher | signals                                        |
| daily 05:00 UTC  | pull_metrics          | analyst    | snapshots, conversions, redemptions, decisions |
| daily 06:00 UTC  | poll_comments         | publisher  | comment signals                                |
| daily 06:15 UTC  | morning_sweep         | researcher | signals, daily brief, problem log              |
| Monday 06:30 UTC | review_strategy       | analyst    | strategy changes, memory, journal, experiments |
| Monday 07:00 UTC | plan_week             | writer     | next week's ideas                              |
| daily 07:30 UTC  | write due scripts     | writer     | scripts for tomorrow, after the last check     |
| every 5 minutes  | dispatch publications | publisher  | runner jobs for due publications               |
| every 3 hours    | listen_x              | researcher | heard replies, each with its reply test variant |
| every 5 minutes  | dispatch replies      | publisher  | runner jobs for replies that go out on their own |

pull_metrics ends by evaluating the persona's running experiments, so there is no separate evaluate_experiments run: a decision lands with its default, learning, journal entry and chat message right after the numbers it rests on. review_strategy runs half an hour before plan_week, so next week's plan follows the pillar weights and defaults it just set.

Scripts are written the day before their episode goes out, not when the week is planned. plan_week leaves ideas; the 07:30 pass queues the write for every idea whose day is tomorrow (and for today's, should one still be an idea), and fails an idea whose day passed unwritten. It runs after the morning sweep, so the writer reads that morning's brief and open problems, and its last check first swaps a reactive concept whose signal went cold for the freshest new signal, with a journal entry saying why. An idea created or moved to today or tomorrow, by the operator or the chat, is queued at once by the same rule (core/episodes.ts `queueScriptIfDue`, the one place a write is queued).

The operator only ever: approves scripts (unless the persona auto-approves), approves publish packages (unless the persona publishes on its own), signs in to tools, sets provider keys, hands over discount codes, and talks to the persona.

### What Formstep must emit

Influstep reads Formstep's PostHog project. Today Formstep sends only `signed_up` from the server (with `$identify` to the landing visitor). For the full funnel Formstep must send these events with the person's `$initial_utm_*` properties intact:

| Event                  | When                                       | Properties                                      |
| ---------------------- | ------------------------------------------ | ----------------------------------------------- |
| `demo_started`         | the visitor opens /try and sends a request | `demo`                                          |
| `signed_up`            | account created (exists)                   | `provider`, `app`                               |
| `trial_started`        | Pro trial begins                           | `plan`                                          |
| `subscription_started` | first successful payment                   | `plan`, `interval`, `discount_code`, `order_id` |

A purchase made with a persona's code reaches Influstep twice, from PostHog and from Polar. Polar is the exact source for those, so the analyst drops the PostHog copy when `discount_code` names a code Influstep handed out; `order_id` (the Polar order) lets it match the two rows outright once Formstep sends it.

Two caveats the report states on screen. PostHog on formstep.io is opt-out by default behind a consent banner, so UTM-attributed numbers undercount; tracked-link clicks and discount-code redemptions are exact and consent-independent. Attribution is first touch.

## Ideas beyond the request

1. **One recording, three cuts.** Record once at 16:9, derive 9:16 and 1:1 with a camera path that follows the cursor (the Formstep explainer already does this in code). Saves a recording per platform.
2. **Hook as the experiment unit.** Most of the lift on short video is the first two seconds. Experiments default to hook variants; concept variants are a second kind.
3. **Comment-reply agent.** The publisher answers comments in the persona's voice, with a directive-controlled allow list of topics, and escalates anything about pricing or bugs to the checklist.
4. **Best time to post.** The analyst learns per platform and per persona when views peak and the planner schedules there.
5. **Persona consistency file.** Each persona keeps a short "bible" (how it speaks, what it never says, recurring phrases). The writer reads it with the directives, so a persona stays the same voice across months.
6. **Search intent, not just trends.** The researcher also pulls "People also ask" and autocomplete for the persona's pillars, so episode titles match what people type.
7. **Evergreen vs reactive mix.** The planner keeps two of five episodes reactive (from this week's signals) and three evergreen (pillars), so a persona ranks over time and still rides news.
8. **Sponsor ramp.** New personas start at sponsor dial 0 for the first ten episodes, then ramp to the configured dial. Already in the planner.
9. **Kill switch and quiet hours.** Pause per persona, plus a global quiet window where nothing publishes (holidays, incidents).
10. **Disclosure by default.** Every publication carries the platform's AI-generated label and the sponsorship disclosure in the first line of the description. EU AI Act and FTC both expect it.
11. **Cross-persona learning.** When an experiment is decided for one persona, the analyst proposes the same experiment to the others as a checklist item.
12. **Runner on a cloud VM.** The runner interface does not assume macOS; a Linux VM with Chromium and ffmpeg can take over recording for tools that do not need the operator's sessions.
13. **YouTube Shorts cut.** A YouTube specialist's format can ask for a second, vertical cut of the same episode published as a Short, so a long tutorial also feeds the short feed.
14. **Multi-tenant later.** Personas already belong to a workspace. Auth (Better Auth, as in Formstep), billing, and per-workspace provider keys turn Influstep into a product.

## Risks worth knowing

- **Platform API access.** TikTok Content Posting and Instagram publishing need app review and a business account; YouTube uploads cost 1,600 of the 10,000 daily quota units, so about six uploads a day per project.
- **Platform policy on AI personas.** YouTube and TikTok allow AI-generated content with labels; undisclosed synthetic people can be removed. The disclosure defaults exist for this.
- **Voice licensing.** ElevenLabs free-tier audio cannot be used commercially even after upgrading; generate on a paid plan from the start.
- **X automation rules.** X's automation rules (help.x.com, "Automation rules", read 2026-10-13) call automated replies to many users on an unsolicited basis an abuse of the reply feature, forbid automated replies to posts chosen by keyword search alone, allow them only to people who asked to be contacted or engaged with the account first, and suspend apps and accounts for spammy or duplicate replies. Engagement on X is built to that line (slice 11): stranger replies need the operator's click, one at a time, and nothing likes or follows on its own. Re-read the rules when the API keys are set up. Search access for the listener is a paid API tier.
- **Attribution is first-touch.** Good for comparing variants, weak for absolute numbers. The report labels them "Signups" and says under every conversion count that they are first-touch and undercount.
